# OCR engine research — 2026-10-13

## Recommendation and evidence policy

Keep the shipped provider as `mock`. For a separately approved real-engine phase, benchmark **tesseract-wasm** first for its smaller documented English download, with **Tesseract.js** as the mature reference and a **PaddleOCR-derived ONNX/WASM** provider as the neural alternative. This is an integration/size recommendation, not an accuracy ranking. The previous scanner's unreliable real-world behavior makes new physical-device comparisons essential; do not reuse its workarounds or claim better reliability from library choice alone.

No engine was installed, executed or benchmarked in this phase. All startup time, recognition time, blueprint-name accuracy and mobile peak-memory values are **unmeasured**. Package metadata below was read directly from the npm registry, without installation. An unpacked npm package is not a minified application bundle, compressed network transfer, full dependency tree or model total. Published claims are labeled; inference/estimates are explicitly distinguished.

## Browser and memory constraints

Use WASM/worker support as the broad baseline, not a GPU-only provider. ORT's published matrix includes WASM on Chrome Android and Safari iOS; this does not verify a particular OCR model on those devices. The tesseract-wasm README lists SIMD-capable browser versions and ships fallback WASM. ocrs JS is alpha. Our new phase is verified with desktop Chromium automation only; no Safari/iPhone/iPad/Firefox/Samsung compatibility claim follows from a README or mock initialization.

An **estimate from pixel arithmetic**, not a heap measurement: 4000×3000 RGBA needs 48,000,000 bytes for one decoded surface before engine heaps, tensors, duplicate buffers or GPU allocations. Bounding target size and reusing one initialized provider should be benchmarked in the future. Record cold/warm p50/p95 times, transferred bytes and peak heap/OS memory with exact browser/device/build versions. Do not multiply workers on low-memory phones without evidence.

## Offline asset plan — not implemented

Self-host pinned JS chunks, worker files, SIMD/fallback WASM, selected English data/models, dictionaries and other runtime dependencies; keep a manifest with sizes/hashes/licenses. Explicitly configure worker/core/model URLs so no implicit CDN fallback occurs. A package import alone does not cache assets.

Integrate versioned asset caching into the future application's single PWA service worker, with completed-cache readiness, failure recovery, compatible JS/WASM versions and safe stale-cache cleanup. Do not cache user photographs. Account for existing legacy scanner registrations without deleting local user records. Browser storage can be evicted; successful online initialization is not proof of offline OCR. ORT worker proxy/threading has CSP and cross-origin-isolation requirements; prefer supported single-thread fallback when necessary. [ORT deployment details](https://onnxruntime.ai/docs/tutorials/web/deploy.html) and [Tesseract asset configuration](https://github.com/naptha/tesseract.js/blob/master/docs/local-installation.md) describe runtime asset separation.

Required future acceptance: initial online installation and cache completion; browser restart; network disabled; provider initialization and recognition of real blueprint title regions; verify no external/network requests and explicit recovery for missing/corrupt assets. No production service-worker/offline configuration was changed, and no offline OCR support is claimed.

## Accuracy evaluation gate

After image acquisition/positioning is approved, compare providers on the identical original-pixel target regions of real prints: clean/tilted/curved/low-light photographs, small qualifiers, similar names and deliberately unknown names. Report exact-name identification and ambiguous/no-match rates separately from OCR character accuracy. Record incorrect unique matches explicitly; never silently guess. This phase contains no real recognition results.
